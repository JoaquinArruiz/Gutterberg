# M24 — Images as pieces

**Goal:** add PNG, JPEG and WebP images to a project as pieces, next to PDF pages, so
someone can print card images (for example proxies to test a deck, or art from a designer)
on the same sheets, with cut marks, bleed and duplex, without making a PDF first.

Read `CLAUDE.md` first. The card-size rule applies: an image gets the size the user chooses
(or one they confirm), never a size picked to make it fit. Use pnpm for every package (never
npm or npx). Every new string goes into both `src/locales/en.json` and `es.json`.

## The idea: an image becomes a one-page PDF

Everything after "open a document" already works on PDFs: the page view, thumbnails, grids,
freeform pieces, Detect pieces, the piece library, the sheets, export. So an image does not
get a parallel path. On import, `card-core` builds a small PDF in which each image is one
page of exactly the chosen size, with the image drawn to fill it. From then on it is a
document like any other.

- **Never resampled unless the user asks** (section 2, very large images). The image's
  pixels go into the PDF as they are; only a matrix scales them to the page. "Content is never rasterised" still holds: the content *is* a raster,
  and it is kept as it came.
  - **JPEG** goes in untouched as a `DCTDecode` stream (read the header for width, height,
    components; no decode). CMYK JPEGs: `DeviceCMYK`, with `Decode [1 0 1 0 1 0 1 0]` when the
    file has the Adobe marker that inverts them.
  - **PNG** is decoded and stored losslessly (`FlateDecode`), with transparency as an
    `SMask`. 16-bit stays 16-bit.
  - **WebP** (lossy or lossless) is decoded and stored losslessly (`FlateDecode`, plus an
    `SMask` for transparency).
  - An embedded ICC profile goes in as `ICCBased` when present; otherwise sRGB is assumed.
  - **EXIF orientation** is applied with the page's matrix (rotate or flip), not by
    re-encoding.
  - Crates: `image` (MIT/Apache-2.0) for PNG and WebP decoding and JPEG headers; lopdf to
    write. Add them to `card-core` only.
- **Where the PDF lives.** In the app's cache folder (`<cache>/images/<hash>.pdf`, where the
  hash covers the images and the chosen sizes). It can always be rebuilt from the images, so
  nothing is lost if the cache is cleared. The project keeps the **images**, not the PDF.
- **One import, one document.** Importing 12 images at once makes one document with 12 pages
  (named after the first image, e.g. "dragon.png + 11 more", renamable), not 12 entries in the
  PDF switcher. Each page gets a 1 × 1 grid that covers the piece, so the 12 pieces show up in
  the piece library straight away. Another import makes another document.

## 1. Import

- **File › Add images…** (and a button on the start screen when nothing is open: "Start from
  images"). Multiple selection. Dropping image files on the window does the same; dropping a
  PDF keeps doing what it does today (or starts doing it, if drop isn't built yet: then only
  images in this milestone).
- Formats: `.png`, `.jpg`/`.jpeg`, `.webp`. Anything else (HEIC, AVIF, TIFF, SVG, GIF) is
  refused with a message naming the file and the formats that work. Not planned for now.
- Size limits: refuse an image over 100 megapixels or 200 MB, with a message (the M10 limits
  style).

## 2. The size dialog

Shown once per import, for all the images in it.

- **Piece size**, with presets (labels in the language files):
  - Standard card (poker, most TCGs): 63 × 88 mm
  - Small card (Japanese size): 59 × 86 mm
  - Tarot: 70 × 120 mm
  - **From the image** (only when every file has a resolution, DPI, saved in it): its pixels
    ÷ DPI
  - Custom: width × height, with a lock to keep the image's proportions.
  - The last size used is remembered (preferences).
- **"The image includes bleed"** switch, with the bleed in mm (default 3 mm, a common
  amount in proxy and print-shop images). On: the page is the piece size plus the bleed on
  every side, and the piece (the 1 × 1 grid) is the piece size in the middle, so M16's
  "bleed from the source" uses the image's own bleed.
- **Images whose proportions don't match the size** (more than 1% off): never stretch them.
  List them and offer, for those files only:
  - **Fit** (default): the whole image, centred, with blank margins on two sides
  - **Fill**: the image covers the piece, centred, and the edges that don't fit are cut off
  Within 1%, the image fills the piece and nothing is said.
- **Resolution check.** For each image, the effective resolution at the chosen size
  (pixels ÷ inches). Under 300 DPI: a note that it may print a little soft. Under 150 DPI: a
  warning that it will look blurry. Never blocks the import. The same mark shows on the
  piece in the library (a small badge with an InfoTip), and in the M11 pre-flight list as a
  warning, not an error.
- **Very large images.** The size only decides the printed size in mm; the pixels stay.
  A 4000 × 5600 px image at 63 × 88 mm is about 1600 DPI: sharp, but heavy. JPEGs go in
  as they are, so they add their file size once; PNG and WebP are stored lossless and can add
  20–40 MB each. So:
  - Show each image's **estimated size in the export** ("adds about 28 MB"), worked out the
    way the cached PDF will store it.
  - Above **1200 DPI** at the chosen size: a note, "Much sharper than any printer needs. The
    exported PDF will be large."
  - A switch, **"Reduce very large images to 600 DPI"**, **off by default**, shown only when
    an image is above 1200 DPI. On: PNG and WebP images above 600 DPI are shrunk to 600 DPI
    with a high-quality filter (Lanczos) and still stored lossless. **JPEGs are never
    reduced**, even with the switch on: that would mean re-compressing them (losing quality),
    and they are compact already. Say so next to the switch.
  - The piece size never changes; only the pixels inside it. The image files on disk are
    never touched: only the cached PDF uses the smaller copy. The choice is saved per page in
    the project (with the other placement settings) and is part of the cache hash, so turning
    it off rebuilds the PDF at full size.
- Mixed sizes in one import: one size for all, as above. Different sizes need separate
  imports. Keep the dialog simple.

## 3. In the project

- `.gtr` **version 3**. A document entry gets a `kind`: `"pdf"` (what every document is
  today) or `"images"`. An images document stores, per page: the image path, its hash, and
  how it was placed (size in mm, bleed, Fit or Fill, reduced to 600 DPI or not). The migration from version 2 adds
  `kind: "pdf"` to every document. Add the Rust migration test, as M16 did for version 2.
- **Opening a project:** rebuild the cached PDF if it's missing, from the images. Moved or
  changed images are handled like moved or changed PDFs in M14 (looked for by hash; a
  changed image asks before replacing). A missing image keeps its page, marked missing, so
  the rest of the project still works.
- An images document can't have pages added to it later in this milestone (import again
  instead). Removing it from the project works like removing a PDF.

## 4. Export and the rest

- Nothing changes in the sheet engine: the cached PDF is a source document. Check that the
  same image printed 50 times is stored **once** in the output (the Form XObject per source
  page should already do this) and add a test that says so.
- Detect pieces on an image page: works as on any page, but the 1 × 1 grid is already right,
  so it's rarely needed.
- PDF permission flags (M15) don't apply to images.

## Tests

- `card-core`: a JPEG goes in byte for byte (compare the stream with the file); a PNG with
  transparency gets an `SMask`; a WebP decodes; EXIF orientation 6 makes a rotated
  placement, not new pixels; the page has exactly the chosen size (with and without bleed);
  Fit and Fill place the image where they should; the cache hash changes when the size does;
  the 600 DPI reduction shrinks a large PNG, keeps its page size, leaves a small one and every
  JPEG untouched, and changes the cache hash.
- Project: version 2 migrates to 3; an images document saves and opens; a missing image is
  reported.
- Frontend: the size dialog (presets, From the image, lock, bleed, Fit/Fill list, the DPI
  notes), with Testing Library.
- Fixtures: tiny generated images (a few KB) in `crates/card-core/tests/data/`, never real
  card art.

## As built

**Engine (`card-core::images`)**
- `probe_image` reads a file's headers without decoding it: format (by extension and by signature), size in
  pixels as shown (EXIF orientation applied), resolution (JFIF, EXIF or PNG `pHYs`), SHA-256, and the limits
  (100 megapixels, 200 MB). `plan_image` is the one place that does the arithmetic: page size, the piece inside
  it (normalized), whether the proportions differ by more than 1%, the resolution at the printed size, the
  quality grade (soft under 300 dpi, blurry under 150), "very large" above 1200 dpi, whether the 600 dpi
  reduction applies, and the estimated size in the export. The dialog, the library badge and the pre-flight
  warning only show what it says.
- `build_images_pdf` writes one page per image. JPEGs go in as their own bytes (`DCTDecode`, header parsed by
  hand, `Decode [1 0 …]` for Adobe CMYK, ICC profile kept); PNG and WebP are decoded and stored losslessly
  (`FlateDecode`, 8 or 16 bits, alpha as `SMask`, ICC kept when its colour space fits). EXIF orientation is a
  matrix on the placement. Fit and Fill are a matrix; Fill adds a clip to the page. The PDF is cached under
  `<cache>/images/<key>.pdf`, the key being a hash of each image's hash and placement.
- `ImageSpec.missing` builds a blank page of the right size, which is how a missing image "keeps its page".
- Errors: `image_unsupported`, `image_too_large`, `image_unreadable`, with codes in both language files.
- Project version 3: Rust migration `v2_to_v3` adds `kind: "pdf"`; tests for it, for the images document and
  for a version-2 file (`project_v3_images.gtr`, `project_v2.gtr`).

**App**
- File › Add images…, a button in the Source tab's page panel, "Start from images" on the start screen, and
  dropping image files on the window (anything that is not a PDF or a project is offered as an image and
  refused by name if it is not one; PDFs are not taken from a drop, as drop was not built before).
- The size dialog (`ImageSizeDialog`), with the last size remembered in preferences (`images.size`; kept by
  "reset to defaults", like the recent files). One import is one document, named after the first image
  ("dragon.png + 11 more"); the pencil next to the name renames it. Each page gets a 1 × 1 grid over the piece.
- Opening a project asks "Where is this image now?" like a PDF, accepts a file with the same hash, asks before
  using a file that changed, and marks an image the user does not find as missing (a notice, a "Missing" badge,
  a blank page, a pre-flight warning).
- Library badge: a "NNN dpi" mark on pieces from images under 300 dpi (amber under 300, red under 150), and a
  "Missing" mark. Pre-flight: a separate amber list ("images that may not print sharp") that does not stop the
  export; it names the images, and clicking one goes to its page.
- The save dialog offers the images document's name instead of the hash-named cache file.

**What changed from the plan**
- The library badge carries its explanation in a native tooltip (`title`), not an InfoTip: a piece in the
  library is a `<button>`, and an InfoTip is a button too.
- "From the image" uses the first image's size when several are imported (one size for all, as the brief says);
  it is offered only when every file has a resolution. With "includes bleed" on, the piece is that size minus the
  bleed on each side.
- The estimated size in the export is a heuristic made from the header (JPEG: the file size; PNG and WebP: half
  of the raw pixels, and the reduction scales it by the square of the resolution ratio), not a measured
  compression. It is labelled "about".
- The pre-flight list is a second panel for warnings, apart from the one for errors, so a warning can never be
  read as a reason the export did not start. In the Print tab it covers the images with pieces on the sheets; in
  the Source tab, the included pages of the document being edited.
- EXIF orientation is read for JPEG, and for PNG and WebP when they carry an EXIF block. PNG is stored without a
  PDF predictor, so a PNG can be larger in the PDF than on disk.
- Fixtures are made by the tests themselves (a few hundred bytes of generated pixels), so no image files are
  committed; the JPEG encoder is a dev-dependency only.

**What I couldn't test**
- The real window: the Tauri commands (`probe_images`, `plan_images`, `build_images_document`), the native file
  dialog with the image filter, dropping files on the window, and the cache folder on each platform. The
  engine behind the commands is tested in Rust, the dialog and flows in Vitest with the engine's answers
  stood in, and the dialog was looked at in a headless browser at 900 × 560 in both themes and in Spanish.
- CMYK JPEGs (the `Decode` array is written, not checked against a real Adobe CMYK file), 16-bit PNGs printed,
  and animated WebP (the first frame is used).
- Printing the exported PDF; the output was checked by rendering it with pdfium (orientation, Fit and Fill).
- `pnpm lint` and the full `pnpm test`, because of the old `.claude/worktrees` copies: `pnpm exec biome check
  src` and `pnpm exec vitest run src` were run instead (clean apart from the 3 warnings and 1 info that were
  already there; all tests pass).
