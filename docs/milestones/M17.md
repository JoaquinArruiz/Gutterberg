# M17 — Detect pieces on a page, locally

Status: **done** (plan approved by the owner; see "As built" at the end). Source tab and `card-core` only; the
Print tab is untouched.

**Goal:** a **Detect pieces** button proposes where the pieces are on the viewed page: no network, no AI. The
proposal is a draft drawn over the page. It is never applied until the user confirms it, and Apply is one undo
step. A weak result says so instead of proposing a wrong grid.

```
page (pdfium) --read_page_data--> PageData { size, objects, grey image }
        --> engines in order --> Proposal[] (best first) --> draft on the page --> Apply / Discard
```

## What the user sees

- Source tab, properties sidebar: a **Detect pieces** section (folded or open like the others) with one button,
  **Detect on this page**. It is off on a skipped page and while a detection runs.
- The result is a **draft** on the page: dashed outlines of the grid (its outer block, the cell lines, and the gaps)
  or of each rectangle, in a colour that is not the real selection's, with a chip: the engine in words ("from the
  PDF's objects", "from repeating edges", "from shapes"), the confidence as a word (Exact / Good / Low), and the
  count ("3 × 3 = 9 pieces" or "7 pieces").
- Buttons: **Apply** (also Enter), **Discard** (also Esc), and **Next proposal** when there is more than one
  (cycles through the other engines' results, best first). Nothing is applied by detecting.
- **Low confidence** (below 0.7) shows an amber line: "Low confidence: check the outlines before applying."
  Below **0.35** a proposal is not offered at all: the section says "No pieces found on this page. Draw the region
  by hand." (and, if an engine had a reason, why: "the art runs across the piece borders", "pieces touch").
- **Apply** a grid: sets the viewed page's group to that grid (`selection` = the block, rows, columns, source gap
  X and Y; gaps linked when equal within 0.05 mm), exactly what drawing the region and typing the numbers does. The
  existing "apply to other pages" dialog then covers other pages of the same size. **Apply** rectangles: they
  become freeform pieces of the page (M18), replacing the page's existing freeform pieces after a confirmation
  when it has any. One undo step either way.
- A draft is dropped when the page, the PDF or the tool changes. It is not saved in the project.
- Words (glossary): "piece", "source gap". New strings in `en.json` and `es.json` ("Detectar piezas", "Detectar en
  esta página", "Aplicar", "Descartar", "Siguiente propuesta", "Confianza baja", "separación de origen"). The
  engines' internal names (`pdf-objects`, `edges`, `blobs`) stay in code only.

## The detector interface (Rust, `crates/card-core/src/detect/`)

```rust
pub trait Detector {
    fn engine(&self) -> &'static str;             // "pdf-objects" | "edges" | "blobs"; M19's AI engine adds its own
    fn detect(&self, page: &PageData) -> Vec<Proposal>;
}

pub struct PageData {
    pub size: PageSize,                           // the page as displayed, points
    pub objects: Vec<PageObject>,                 // kind (image | rect-path | line-path | other), bounds in points
    pub grey: Option<GreyImage>,                  // low-resolution render, 8-bit grey, with its points-per-pixel
}

pub struct Proposal {
    pub kind: ProposalKind,                       // Grid { bounds, rows, columns, source_gap_x_mm, source_gap_y_mm }
                                                  // | Rects(Vec<OrientedRect>)
    pub confidence: f64,                          // 0..1
    pub engine: String,
    pub notes: Vec<Note>,                         // codes the UI words: missing_cells, crop_marks, touching, ...
}
```

- Everything in **points, top-left origin** (like `layout` and `sheet`); the frontend turns it into normalized
  coordinates through `src/lib/coordinates.ts` (`pdfToNormalized`, `orientedFromPoints`), as it does for every other
  geometry.
- `detect_page(data, &[&dyn Detector]) -> Vec<Proposal>` runs the engines in order, drops proposals under 0.35,
  sorts by confidence, and **stops early** when an engine returns one at 0.85 or more.
- A new engine (the optional AI engine of M19) implements the trait and is added to the list; the command, the draft
  and the UI do not change.
- The engines are pure functions of `PageData`, so they are tested without pdfium; only `read_page_data` needs it.

## Engines, in order

Shared constants (one block, `detect/mod.rs`): smallest piece side **15 mm**; a candidate larger than **60 %** of
the page in both directions is the page, not a piece; positions match within **0.3 mm**, sizes within **0.5 mm**
(the same tolerance as `SIZE_TOLERANCE_MM`); bands **≥ 0.7 good, 0.35 to 0.7 low, < 0.35 dropped**.

1. **PDF objects (exact).** From pdfium's page objects, in the displayed frame (bounds converted with the exporter's
   `PageFrame`, so rotated pages and CropBoxes land where the preview shows them). Candidates are images and
   axis-aligned rectangle paths (a closed path of four right-angled segments; a fill and a stroke of the same
   rectangle count once), plus the children of a page-sized form one level down (an exported sheet is made of forms).
   Group candidates of one size, sort their centres into columns and rows (0.3 mm), and accept a grid when the
   pitches are regular (≤ 0.3 mm spread): that gives bounds, rows, columns and the source gap (pitch minus size), to
   a fraction of a millimetre. Confidence 0.95 when every cell of the grid has an object; minus 0.25 with
   `missing_cells`; at most 0.6 when there are only 2 or 3 objects. Thin line paths in the margins that line up with
   the grid's boundaries are crop marks: `crop_marks` note and +0.04 (cap 0.99). Several sizes on one page give
   one proposal per size group, best first.
2. **Repeating edges (flat sheets).** Render grey (1600 px on the long side, about 0.19 mm per pixel on A4).
   Profile `P(x)` = the horizontal gradient `|I(x+1) - I(x-1)|` summed down the page; `Q(y)` likewise across.
   Card borders are tall, regularly spaced peaks. Find the pitch by autocorrelation of the profile (high-passed,
   limited to 15 mm and up), refine every peak with a parabola for sub-pixel position, and walk the peaks from the
   strongest to get the columns (rows the same). With gaps, runs of plain background across the whole page height
   (no gradient) that repeat at the pitch are the gaps: the piece width is the pitch minus the gap. The block's outer
   bounds come from the first and last boundary. Accuracy target 0.5 mm. Confidence `0.5 · peak strength + 0.3 ·
   share of the expected boundaries that have a peak + 0.2 · share of the page's content the block covers`, capped at
   **0.9**: an inferred grid never reads as exact. Fewer than 2 columns and 2 rows is not a grid.
3. **Blobs (scans, loose pieces).** Render grey (1000 px). The scanner background is the most common tone along
   the page border; a pixel is foreground when it differs by more than Otsu's threshold on that difference. Open and
   close the mask a pixel or two, label connected components, drop those under 15 mm, and fit the minimum-area
   rotated rectangle to each blob's convex hull (rotating calipers). One `OrientedRect` per piece, tilt kept, angle
   normalized to ±45° with width along the nearer axis, reading order. A blob whose area is under 85 % of its
   rectangle is not a clean piece (merged or not a card) and lowers the score. Confidence = mean fill ratio × a
   size-consistency factor (1 when sizes agree within 5 %, down to 0.8), × 0.7 when only one blob was found or a blob
   touches the page edge, capped at **0.9**. A mask where most blobs are merged or cover the page gives
   `touching` and a score under 0.35, so nothing is offered.

Reported as low confidence or dropped, never guessed: art that runs across borders with no visible line, pieces
touching on a scan, white pieces on a white bed, a page that is one photograph.

The weights above are the starting values; they are tuned once against the test fixtures and then fixed in the
constants block, with the fixtures as the evidence.

## IPC and threading

- `RenderWorker` gets `Work::Detect(doc, page, Reply<Vec<Proposal>>)`: pdfium owns the page, so reading objects and
  the grey render happen on its thread (`read_page_data`, in `render.rs`); the engines then run on the same thread
  (milliseconds) or on the caller, whichever keeps the worker free (the data is plain). Never superseded, normal
  priority.
- Command `detect_pieces(document_id, page_index) -> Vec<Proposal>` in `src-tauri/src/commands/detect.rs`, a thin
  wrapper like the others. Proposals serialize with `serde` (snake_case, `kind` tag), parsed with Zod in
  `src/lib/detect-api.ts`.
- No new dependency. The outline named `imageproc`; it is not needed for this (profiles, autocorrelation, labelling and
  a convex-hull rectangle are a few hundred lines) and pulls in heavy dependencies, so the algorithms are written in
  `card-core::detect` on top of the `image` crate already used.

## Frontend

- `src/lib/detect.ts`: pure functions from a proposal to what the stores take (`gridFromProposal` →
  `{ selection, rows, columns, sourceGapXMm, sourceGapYMm, sourceGapLinked }`, `cardsFromProposal` →
  normalized `OrientedRect[]`), the confidence band, and the labels' keys.
- `editor-store`: `detection` = `{ page, proposals, index } | null`, `detecting` flag, actions `runDetect`,
  `nextProposal`, `discardDraft`. Session state, like the picked piece.
- `layout-store`: `applyDetectedGrid(page, grid)` and `applyDetectedPieces(page, rects)`, each one `set` so undo
  history gets one step (`applyDetectedPieces` replaces the page's freeform pieces and keeps turns, sizes and order
  consistent the way deleting pieces does).
- `DetectSection` (sidebar), `DetectOverlay` (viewport; no pointer events, so tools keep working underneath), the
  chip. Strings in both catalogs; no new preference.

## Tests

Rust (`crates/card-core/tests/detect.rs`, `detect_render.rs`; fixtures are built in the tests, no binary files):

- **Vector sheet, exact:** `sample_pdf()` (3 × 3, 63.5 × 88 mm, edge to edge) gives a grid of 3 × 3 with bounds and
  gap within 0.05 mm of `sample_grid(0.0)` and confidence ≥ 0.9, engine `pdf-objects`; a sheet exported with
  `export_sheets` (forms, 6 mm gaps) gives the 6 mm source gap; a 2 × 4 page with one cell missing gives
  `missing_cells` and a lower score; rotated and CropBox'd pages (the `sample` helpers) give the displayed frame; a
  page with a full-page background image and the cards on top still finds the cards; crop marks add the note.

- **Edge-to-edge raster:** the sample page rendered with pdfium and put back into a PDF as one image (no vectors):
  `pdf-objects` offers nothing, `edges` gives 3 × 3 with each boundary within 0.5 mm; the same with white gaps;
  a 2 × 5 sheet; a page with margins around the block.
- **Scan:** a generated image (plain bed with noise, 6 cards tilted between -12° and 15°, one rounded) in a PDF:
  `blobs` gives 6 rectangles, centres within 1 mm, angles within 1°, sizes within 1 mm, in reading order.
- **Low confidence:** a blank page, a noise image, a page-sized photograph gradient and touching tilted cards offer
  nothing or a proposal under 0.7, never a confident wrong grid; a clean case is the control.
- **Interface:** the engine list with a fake engine (the M19 shape), early stop at 0.85, sorting, the 0.35 cut.

## Out of scope

- Applying a detection to several pages at once or to a whole PDF (the existing "apply to other pages" covers pages
  of the same size); detecting on every page automatically.
- Perspective correction, deskewing the page, round or custom shapes (pieces stay rectangles; a round token is
  detected by its rectangle at best).
- Learning from corrections, OCR, reading cut lines drawn as dashed or curved paths, grids with unequal pitch.
- The AI engine and its settings (M19); only the interface it plugs into is built here.
- A new hint or tour for the button, and a project-file change (the draft is session state).

## Decisions (approved by the owner)

1. No `imageproc` or other new dependency; the algorithms are written in `card-core`.
2. Under 0.35 nothing is offered; 0.35 to 0.7 is offered with a "low confidence" warning; Apply is always a click.
3. Detection works on the viewed page only; other pages use the existing "apply to other pages".
4. Rectangle proposals replace the page's freeform pieces (asking first when there are some).
5. Inferred grids (`edges`, `blobs`) are capped at 0.9 so only `pdf-objects` can read as exact.

## As built

Where the implementation settled on details the plan left open, or went another way:

- **Module.** `crates/card-core/src/detect/`: `mod.rs` (the types, the `Detector` trait, `detect_page`, the constants
  block), `objects.rs`, `edges.rs`, `blobs.rs`, and `read.rs` (the only part that needs pdfium: `read_page_data`).
  `RenderWorker::detect(document, page)` reads the page and runs `detect_page(&data, &default_engines())` on the
  render thread; the command is `detect_pieces` in `src-tauri/src/commands/detect.rs`. No new dependency: the
  profiles, autocorrelation, labelling, hulls and the rotating-calipers rectangle are written on top of `image`.
- **What comes back.** `Detection { proposals, reasons }`: proposals worth offering (confidence 0.35 or more) best
  first, ties broken by what they cover; `reasons` (`merged_pieces`, `no_regular_pattern`) only when there are no
  proposals. A `Proposal` has `kind` (`grid` or `rects`, flattened into the object), `confidence`, `engine` and
  `notes` (`missing_cells`, `crop_marks`, `few_objects`, `uneven_sizes`, `touches_edge`, `one_piece`, `merged_pieces`).
  `detect_page` ends the search at 0.85. A shared file, `tests/data/detection.json`, is read by a Rust test (which
  also writes it back) and by `detect.test.ts`.
- **Engine 1 (objects).** Candidates are images and axis-aligned four-corner paths, read from the path's own points
  (not from pdfium's bounds, which include half the stroke width), so a fill and a stroke of one rectangle are one
  candidate and positions are exact. Page space is turned into the displayed page (`/Rotate` and the visible box)
  by `DisplayFrame`, checked against `sample_grid_for` for all four rotations with and without a CropBox. **Forms:**
  the plan said children of a page-sized form are read; a form's bounds are its content's, not the page's, and an
  exported sheet is many forms each clipped to one piece (their content reaches past what they show), so this reads
  inside a form **only when it is the page's single form** (the "everything wrapped in one form" case). Exported
  sheets are therefore not read exactly; the edges engine finds them. Same-size candidates are gridded by clustering
  lefts and tops (0.3 mm); the pitch must be regular to 0.3 mm; overlapping objects are not a grid; confidence 0.95,
  minus 0.25 for missing cells, capped at 0.6 for fewer than four cells, plus 0.04 for crop marks. Irregular
  same-size objects give nothing (they are not offered as rectangles).
- **Engine 2 (edges).** One grey render, 1600 px on the long side, serves both image engines (the plan said 1000 px
  for blobs; one render is simpler and the blob pass is fast enough). Profiles of the horizontal and vertical
  gradient are sharpened (a 5 mm moving average removed), their peaks found to sub-pixel and **merged when closer
  than 1.2 mm** (a printed line gives a peak on each side, and two lines that meet look like a gap as wide as the
  lines), so a gap narrower than that is read as pieces that touch. Pitch candidates are the autocorrelation maxima;
  each is refined by least squares against the peaks and tried as a single comb (pieces touch) and, for every offset
  the other peaks suggest, as a comb pair (gaps). The model that explains the most peak height wins, and a comb pair
  only counts when the interval taken as the gap is **plain** (at most a fifth as busy as the piece). Bounds, cell
  size and gap are then measured from the peaks the boundaries snap to, not from the pitch. An axis with no pattern is
  one cell across the ink (`few_objects`, lower confidence); no pattern on either axis is the reason
  `no_regular_pattern`. Confidence is `0.5 · autocorrelation + 0.3 · share of boundaries with a peak + 0.2 · share of
  the ink the block covers`, capped at 0.9.
- **Engine 3 (blobs).** Background = median of the page border; foreground by Otsu on the difference (and never below
  a contrast floor); open then close; 4-connected components; each blob's outline pixel corners give the convex hull,
  and its minimum-area rectangle (angle normalized to ±45°, width along the nearer axis) is the piece. Blobs under
  15 mm or covering most of the page are dropped; a blob whose hull fills under 85 % of its rectangle is "not clean"
  (a `merged_pieces` note, ×0.6, or the reason when nothing clean is left). One piece ×0.6 (`one_piece`), touching the
  page edge ×0.7, uneven sizes down to ×0.8, capped at 0.9. Output is in reading order.
- **Order and ties.** A page that is exact for engine 1 stops there. With a missing cell engine 1 scores 0.70, so the
  edges engine's full grid can rank above it; both are in the list and "Next proposal" reaches either.
- **Frontend.** `detect-api.ts` (Zod), `detect.ts` (pure: `confidenceBand` exact/good/low, `gridFromProposal`,
  `piecesFromProposal`, `pieceCount`, all through `coordinates.ts`), `detect-actions.ts` (`runDetect`, `applyDraft`,
  `discardDraft`, and subscriptions that drop the draft when the page, the PDF or the tool changes). The draft lives in
  `editor-store` (`draft`, `detecting`, `detectError`). `layout-store.applyDetectedGrid` and `applyDetectedPieces`
  are single `set` calls, so each is one undo step; the pieces one also removes the replaced pieces' edits and backs
  and tells the Print stage through the same listeners as deleting a piece, so copies and selection follow.
- **UI.** `DetectSection` (sidebar, before the layout sections, for pages that are not skipped) holds the button, the state, errors and the "nothing found" message with its reason. `DetectDraftBar` sits at
  the bottom of the page view: what the draft is, the engine in words, Exact / Good / Low confidence, the count, the
  notes, **Apply**, **Next proposal** (when there is more than one), **Discard**; Enter and Esc work unless a field has
  focus. Replacing existing freeform pieces is the Apply button's own label ("Replace 2 pieces"), not a dialog.
  `DetectOverlay` draws dashed amber outlines (cells of a grid, or each rotated rectangle) and takes no pointer event.
  The glossary has **proposal / propuesta**; the new strings are in both catalogs for the owner's review.
- **Tests.** `tests/detect.rs` (29 engine, interface, serde and pdfium tests), `src/lib/detect.test.ts`,
  `src/lib/detect-actions.test.ts`, `src/components/editor/detect.test.tsx`. The edges and blobs tests are on grey
  images made in the test (a sheet with borders, art and gaps; a scan with noise and tilted, rounded pieces) and,
  through pdfium, on the sample page and a gapped vector sheet rendered and put back into a PDF as one picture.
- **Not done / limits.** Only generated fixtures were available: no real publisher PDF or phone/scanner image was
  tried, and the weights above were tuned on those fixtures, so real files may need them adjusted (they are in the
  constants of each engine). A gap narrower than about 1.2 mm cannot be told from a line; pieces of one flat colour with
  no border give the edges engine little to find; a grid of pieces that are not all the same size is not offered by
  engine 1. Not driven by hand in the Tauri window while writing this (the draft's look and the keyboard feel are only
  covered by jsdom tests).
