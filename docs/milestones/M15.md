## Step 1 — Releases and updates

**Goal:** pushing a tag such as `v1.1.0` builds the app for every platform and prepares a
GitHub release; when the owner publishes it, every installed copy can see and install the
update from Preferences, and a toast says so.

Uses the official [tauri-action](https://github.com/tauri-apps/tauri-action) as shown in
Tauri's guide [GitHub pipelines](https://v2.tauri.app/distribute/pipelines/github/), and the
Tauri **updater** plugin. Read both pages before starting; follow them where this brief
doesn't say otherwise.

### Versions and tags

- **Semantic Versioning**, `MAJOR.MINOR.PATCH`: PATCH for bug fixes only, MINOR for new
  features that keep old `.gtr` files working, MAJOR for big or breaking changes (a project
  migration, a redesign). The updater requires this format.
- Tags have a `v` (`v1.1.0`); the version in the files doesn't (`1.1.0`). Pre-releases, if
  ever: `v1.2.0-beta.1`.
- **One place for the version:** `package.json`. Point `tauri.conf.json`'s `version` at it
  (`"version": "../package.json"`). `src-tauri/Cargo.toml` keeps its own (Cargo needs it):
  the workflow fails if the three disagree with the tag.
- The first public version is up to the owner (`1.0.0`, or `0.9.0` to say "early").

### Release notes: `CHANGELOG.md`

- At the repo root, in the "Keep a Changelog" layout: an `## Unreleased` section at the top
  with `### Added`, `### Changed`, `### Fixed`, then one section per version,
  `## 1.1.0 (2026-11-02)`, newest first.
- At release time the `Unreleased` heading becomes the version and date, in the same commit
  as the version bump.
- The workflow takes the section of the tag's version and passes it to tauri-action as the
  release text. From there it reaches the GitHub release page and `latest.json` (what the app
  shows). A missing section fails the workflow.
- English only for now. (Later, if wanted: a `CHANGELOG.es.md` read the same way, with the
  app picking the notes in its language.)
- Fixing notes after a release: edit `CHANGELOG.md` and re-run the workflow for that tag
  (it replaces the release's files). Editing the text on GitHub alone does **not** change
  `latest.json`.

### The workflow (`.github/workflows/release.yml`)

- Runs on `push: tags: ['v*']`. `permissions: contents: write`.
- Matrix: `macos-latest` twice (`aarch64-apple-darwin` and `x86_64-apple-darwin`),
  `ubuntu-22.04`, `windows-latest`. Linux installs the WebKitGTK packages from the Tauri
  guide.
- Steps: check out, pnpm and Node, Rust with the target, `pnpm install --frozen-lockfile`,
  fetch pdfium for that platform with `scripts/fetch-pdfium.sh <target>` (pinned and
  checked, as in M8; add targets if missing), check the tag against the versions and that
  `CHANGELOG.md` has its section, generate `THIRD_PARTY_LICENSES` (step 2), then
  `tauri-apps/tauri-action` with `tagName: v__VERSION__`, `releaseName`, `releaseBody` from
  the changelog section, **`releaseDraft: true`**, `prerelease: false`.
- Outputs: `.msi`/`.exe` (Windows), `.dmg` and `.app.tar.gz` (macOS), `.AppImage` and
  `.deb` (Linux), with pdfium inside each, their updater signatures, and `latest.json`.
- Secrets: `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
  (`GITHUB_TOKEN` is automatic). Code-signing secrets only if the owner decides on signing
  (below).
- Keep the existing `ci.yml` as it is; the release workflow is separate.

### The owner does once (the session explains, can't do it)

1. Generate the updater key: `pnpm tauri signer generate -w ~/.tauri/gutterberg.key`.
   Put the private key and its password in the repo's secrets (Settings › Secrets and
   variables › Actions). **Keep a backup of both somewhere safe** (a password manager): if
   the key is lost, installed copies can never update again. The public key goes in
   `tauri.conf.json` (the session adds it when the owner pastes it).
2. The repo must be **public** before the first release, so apps can download
   `latest.json` and the installers without a token.
3. Settings › Actions › General › Workflow permissions: "Read and write".

### Releasing (also written up in `docs/releasing.md`, for the owner)

1. Move the `Unreleased` notes under the new version in `CHANGELOG.md`; bump the version in
   `package.json` and `src-tauri/Cargo.toml` (`cargo build` refreshes `Cargo.lock`).
2. Commit ("Release 1.1.0"), then `git tag v1.1.0` and `git push origin main v1.1.0`.
3. Watch the run in the Actions tab. If a build fails: fix, delete the tag
   (`git tag -d v1.1.0`, `git push origin :refs/tags/v1.1.0`) and the draft, and tag again.
4. Open the draft release, check the files and notes, press **Publish**. Only then do apps
   see it (GitHub's `releases/latest` skips drafts and pre-releases).
5. Testing the updater before going public: release `0.9.0`, install it, release `0.9.1`,
   and check that 0.9.0 offers and installs it.

### In the app

- **Plugins:** `tauri-plugin-updater` and `tauri-plugin-process` (for the restart), their JS
  packages, and their permissions in `src-tauri/capabilities/default.json` (`updater:default`,
  `process:allow-restart`). `bundle.createUpdaterArtifacts: true`; the updater's
  `endpoints` is
  `https://github.com/JoaquinArruiz/Gutterberg/releases/latest/download/latest.json` and its
  `pubkey` the owner's public key. Windows install mode `passive`.
- The updater talks to the network from Rust. Update `CLAUDE.md` (today it says `card-ai`
  is the only crate that does): the updater check is the other one, and it sends nothing but
  the request for `latest.json` and the download.
- **When it checks:** about 10 seconds after start, at most once a day (`prefs.updates.lastCheck`),
  never during an export. Offline or a failed check stays silent; it shows only in
  Preferences, and only after a manual check.
- **Preferences › Updates** (a new section, icon `Download`, right after Help):
  - "You have **1.1.0**." and, when there is one, "**1.2.0** is available", with its notes
    ("What's new in 1.2.0"). Show the notes as plain text with line breaks and list bullets;
    never as HTML.
  - **Check for updates** and "Last checked: …".
  - **Download and install**, with progress, then **Restart now** / **Later**. If the project
    has unsaved changes, ask to save first (the usual dialog).
  - **"Tell me about"** (RadioCard): **All updates** (default) / **New features** (a new
    MINOR or MAJOR; skips patches) / **Major versions only** / **Never** (I'll check myself).
    This only decides the toast: this section always shows a newer version when there is one.
    Updating always installs the newest version (from 1.0 straight to 2.0, if that's the
    newest).
- **Toast "update available"**, a normal toast (not a HintToast: tips can be turned off
  for good; this is about one version): "Gutterberg 1.2.0 is available" with **What's new**
  (opens Preferences › Updates), **Update** and **Skip this version**
  (`prefs.updates.skippedVersion`; quiet until a newer one). Obeys "Tell me about". If the
  app has no general toast yet, build a small one in `src/components/ui` (bottom corner,
  one at a time, closes on Esc, announced to screen readers) and use it for both toasts.
- **Toast after updating**, so the user knows it went well:
  - Before installing, save `prefs.updates.pending = { version, notes }`.
  - On the next start: the app's version equals `pending.version` → "Updated to 1.2.0" with
    **What's new** (the saved notes), shown once, then clear `pending`. The version is older
    than `pending.version` → "The update to 1.2.0 didn't finish" with **Try again**.
  - Also keep `prefs.updates.lastRunVersion`; a first install shows no toast.
- **Experimental features:** Preferences › **Experimental** (icon `FlaskConical`), switches
  for unfinished features, off by default, labelled "May change or disappear in a later
  version". The list is `src/lib/experimental.ts` (id, text keys); the code checks a flag
  with `useExperimental(id)`. The section is hidden while the list is empty. A beta update
  channel (Stable / Beta, pre-release tags, a second `latest-beta.json`) is **later**, not
  part of this milestone.
- Preferences version bump for `updates` and `experimental`, with a migration test.
- Tests: the version comparison and "Tell me about" (patch, minor, major, skipped version,
  pre-1.0), the after-update toast (success, failure, first install), the notes rendering
  (no HTML), with the plugins mocked.

### File association

- Register `.gtr` in `bundle.fileAssociations` (`tauri.conf.json`,
  name "Gutterberg project", role Editor), so double-clicking a project opens Gutterberg.
  Handle the opened file at startup (command-line argument on Windows and Linux) and
  through the "opened" run event on macOS, then load it with the M14 checks. The welcome

  - Declare a unique type ID for the format: `dev.joaquinarruiz.gutterberg.project`

    `application/vnd.gutterberg.project+json` (Linux desktop entry). These are declarations
    in the Tauri bundle config only; nothing has to be registered anywhere.

### Signing

- macOS notarisation needs an Apple developer account (paid); Windows signing needs a
  certificate. Decide with the owner whether unsigned builds are acceptable first. The
  updater works either way (its own key, above).
  - If builds ship unsigned, the README explains the first-launch warnings: macOS
    (right-click › Open, or System Settings › Privacy & Security › Open Anyway) and Windows
    SmartScreen ("More info" › "Run anyway").
- On Linux the updater replaces the AppImage; `.deb` users update by downloading the new one.
  Say so in the README's download section.

  3. No restrictions: unchanged.

  Read the flags when the PDF opens, so the UI can say so early (a small lock badge with
  the reason). Add fixtures for each case. Replace the README line about export removing
  encryption with the new behaviour.

## Step 4 — Clean the repo (always last)

**Goal:** the public repo looks like a normal project: no milestone briefs or AI working
notes, while everything that was learned stays available, and future features still have a
place to be planned. **Follow this order exactly.** Nothing is deleted before what replaces
it exists, and nothing is deleted before the tag in point 4.

1. **`docs/architecture.md`.** Write it from the "As built" sections of every brief and the
   README's Architecture section: how the parts fit (card-core, card-ai, the Tauri shell, the
   frontend), the engine pipeline (extract, paginate, export, finish), coordinates and units,
   the project format and its migrations, previews and caching, detection, AI Mode, hints,
   languages, updates, and the decisions table from `docs/milestones/README.md`. Written for
   humans: what and why, not a history of sessions. Show it to the owner.
2. **`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`.**
   - `AGENTS.md` (read by most AI coding tools): the project summary, layout, commands, code
     rules and glossary from today's `CLAUDE.md`, plus the repo rules that apply to every
     contributor: pnpm only (never npm or npx); one-sentence commit messages; no AI author,
     co-author or session lines in commits; don't commit, push, create branches or pull
     requests unless asked; no license headers. And how features are planned from now on
     (point 6).
   - `CLAUDE.md` becomes one line: `@AGENTS.md`.
   - `CONTRIBUTING.md` (for people): set-up, the checks to run, how to open an issue or a
     pull request, the CLA if the owner adopted one, and that AI-assisted contributions are
     welcome under the same rules (`AGENTS.md`), reviewed like any other.
   - Add AI tool leftovers to `.gitignore` (`.claude/worktrees/`, `.claude/settings.local.json`,
     `CLAUDE.local.md`).
3. **The owner's personal rules.** Only what is personal leaves the repo: the commit identity
   (`Cac0 <joaquinarruiz@gmail.com>`, which `git config` already sets) and "show the commit
   message and wait for approval". The session gives the owner the text to put in
   `~/.claude/CLAUDE.md` on their computer. Note for the owner: cloud sessions (claude.ai/code)
   don't read that file, which is why the shared rules stay in `AGENTS.md`. **Wait until the
   owner confirms it's done.**
4. **Tag before deleting.** Commit points 1–3, then an annotated tag on that commit:
   `git tag -a pre-cleanup -m "Milestone briefs before the repo cleanup"`, pushed when the
   owner says so. Every brief stays recoverable with `git show pre-cleanup:docs/milestones/M13.md`.
5. **Delete**, in one commit: every brief in `docs/milestones/` and its `README.md`, except

6. **From then on** (written in `AGENTS.md`): a feature being built may have one brief in
   `docs/milestones/` (e.g. `images-v2.md`). When it's done, what's worth keeping moves into
   `docs/architecture.md`, the user-facing change goes into `CHANGELOG.md`, and the brief is
