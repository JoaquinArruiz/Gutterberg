## 1. Wheel scrolls the sheet strip

Today the strip under the sheet (`SheetStrip.tsx`) is `overflow-x-auto`, so only Shift+wheel, a trackpad or the
scrollbar move it. Add a wheel handler: when the strip overflows and the event is a vertical wheel (`deltaY` larger
than `deltaX`, no Ctrl), turn `deltaY` into `scrollLeft` and `preventDefault`. A trackpad's sideways swipe keeps
working as now. React's `onWheel` is passive, so it needs a native listener with `{ passive: false }`.

The Source tab's Pages panel docked at the top or bottom (horizontal orientation) has the same problem, so the same
small hook (`useWheelScrollsSideways`) goes there too.

Not planned: the wheel over the big sheet preview changing sheet. It would surprise people expecting zoom later, and
the arrows already do it. No toast is needed; the strip scrolling under the wheel explains itself.

## 2. Hold right-click to see a piece big

Pressing and holding the right button on a piece (on the sheet preview, in the sheet strip, and in the piece
library) opens a lightbox: the piece alone, as large as the window allows, straightened and turned as it prints,
with its name or label and source page under it. Releasing the button closes it; so do `Esc` and a click.

- Render through `useCardImage` at the lightbox size with priority "page", so it is sharp, not the stretched thumbnail.
- A right-click without hold (under ~250 ms) keeps opening the context menu where there is one (the library has
  none today, so nothing changes there).
- The web view's own context menu must stay suppressed during the hold.
- A help tip on first use of the Print tab with many similar pieces is not worth it; it goes in the "Find a piece on
  the sheet" tutorial as one extra step, and in `docs/controls.md`.

Accessibility: the lightbox is a dialog with the image's alt text; the same view could open from a "View larger"
menu item for keyboard users.

## 4. Readme to ship with a `.gtr`

The idea: a publisher puts `my-game.gtr` next to `my-game.pdf` in the download, so players get the pieces marked and
a print layout ready. Two things are needed, and the first matters more than the readme:

1. **Opening a shared `.gtr` without "Where is this file now?"**. A project stores the PDF's absolute path
   (`C:\Users\publisher\...`), so on the player's computer every PDF is asked for by hand. Fix in
   `locateDocuments` (`src/lib/project-actions.ts`): when the saved path is missing, look first next to the `.gtr`
   for a file with the same name, then for any PDF in that folder with the same hash, before asking. No format change.
   Forward compatibility is already there: a project of an older version opens in every newer app (migrations up to
   version 7 today); a newer one is refused by an older app with a message to update.
2. **File › Save for sharing…**: saves the project as usual and writes `<name>-Gutterberg-readme.txt` beside it, from
   a template in both languages (the one the app is in): what Gutterberg is, that this `.gtr` has the pieces marked
   and a print layout, where to download the app (the address from item 3), the steps (install, open the `.gtr`,
   keep the PDF in the same folder, Print tab, Export), and the app version it was made with. The publisher can edit
   the text afterwards; nothing about it is read back.

A PDF version (one page, the logo, a small before/after diagram) would look nicer and could be built with `lopdf`
in `card-core` as vector text, but it is a lot more work for the same words. Suggested: TXT in 1.3.0, PDF later if
publishers use it.

No donation link for now.

## 5. Real export name in the toolbar

The Print tab toolbar shows "New-PDF" until you rename it, but Export suggests `<first source>-print.pdf`
(`pickExportPath` in `src/lib/tauri.ts`). Show that same name (from one shared function, so they can't drift) in grey
as the placeholder when there is no chosen name, and when the field opens for editing, put that text in it with the
caret at the end instead of selecting all, so `Home`/`End` add to it. A name equal to the suggestion is stored as
"no chosen name", as "New-PDF" is today, so it keeps following the first source.

## 6. `Delete` removes the focused page

In the Source tab's Pages panel, a page thumbnail that has focus (clicked, or reached with `Tab`) is removed from
view with `Delete` or `Backspace`, the same as its "Remove page" menu item: one undo step, the last page in view
stays, and the page goes to "Removed pages". It does not delete anything from the PDF.

The global key handler in `App.tsx` already uses `Delete` for picked freeform pieces. The thumbnail handles the key
itself and stops it, so with a thumbnail focused it removes the page, and anywhere else it deletes pieces as now.
`Shift`/`Ctrl`-click to remove several pages at once is a natural next step but not asked for; left out.

## 7. Cut marks where the gaps cross

A user's screenshot: Ticks in the margins, with nothing between the pieces, so cutting the inside needs a ruler laid
across the whole sheet. Today "Lines in the gaps" draws full lines through the middle of every gap, which crosses at
those points, but it is a line all the way across.

Proposed: Print settings › Cut marks › **Also where gaps cross** (on/off, Ticks style only). At each point where a
horizontal and a vertical gap meet, a small cross of the same line, colour and width, its arms the Length setting
but never longer than reaches the bleed of the pieces around it. Gaps narrower than the line plus clearance get no
cross, with the existing "gap too narrow" warning. With duplex and "Also on back sheets" they follow the mirrored
backs as the ticks do. The CLI exports it as saved.

Code: `marks_for` in `crates/card-core/src/finish.rs` already finds the gaps on each axis (`gaps_along`); the crosses
are the pairs of gaps whose spans both contain pieces on all four sides. `MarkOptions` gets `inner_crosses: bool`
(serde default false, so old projects open without it); tests in `crates/card-core/tests/`.

## 8. Fill colour behind pieces, and for the sheet

Two settings under a new Print settings › **Background** section:

- **Sheet colour**: paints the whole sheet first (default none = white paper). Black sheets mean whatever is not a
  piece prints black. Ink heavy; the section says so.
- **Behind the pieces**: paints a rectangle under each piece, the piece plus its bleed, before its content. For
  cards with rounded corners or a missing corner, that colour shows in the corners, so a black-bordered card is cut
  with black corners instead of white ones.

Both are vector fills (`re f` in the content stream) drawn under the original content, so nothing is rasterised.
The preview's `PlacedCard` (now `bg-white`) and `sheet-page` use the same colours.

Limit to say in the hint: it only shows where the source has nothing drawn. Many PDFs leave the corners empty, but
some paint them white, and scans and images always have white corners; there the fill is covered. For those, item 9.

## 9. Fill the edges of pieces (algorithm and AI)

What already exists: Print settings › Bleed › Mirror extends every piece by reflecting its edge strip, without
rasterising anything. 1.3.0 adds two more Bleed sources:

### Edge colour (algorithm)

Render the piece small, take the dominant colour of its outer band, and paint the bleed in that colour as a vector
rectangle, under the piece. Per piece, automatic, offline, free. With item 8's "behind the pieces" it also fills
empty corners.

### Fill with AI (AI Mode only)

In 1.3.0, not later.

**Providers.** It needs a model that returns a picture, which the current adapters never ask for (they all read a
JSON reply). Works with Gemini (an image model through `generateContent` with an image in the reply) and with
OpenAI-compatible servers that have the image edits endpoint (`/v1/images/edits` with a mask, e.g. OpenAI's image
models). Anthropic and Ollama have no image output: the option is shown disabled with that reason.
Preferences › AI Mode gets a second field, **Image model**, with the same model list and reload as the Model field
(1.1.0), since the chat model cannot draw.

**What is sent.** For each chosen piece, the app renders it at print resolution (300 dpi, capped near 1024 px on the
long side) centred on a canvas that is larger by the bleed, plus a mask: the band outside the piece is to be painted,
the piece itself is kept. The prompt asks to continue the artwork outward and nothing else. The usual confirm notice
before an AI action says the server, the number of pictures, and that each is a paid image request.

**What comes back is checked** like every AI reply: right size, a picture at all; then only the bleed band of it is
kept (the inside is cut away by the app, so the model can never change the piece). Anything else is an error for that
piece, and the rest go on.

**Review before applying.** A dialog shows each piece with its fill, before and after, and a tick per piece; Apply
keeps the ticked ones, in one undo step. Pieces without a fill (refused, failed, not ticked) use Mirror.

**Where fills are kept.** They are pictures, too big for the `.gtr` text. Saved as PNGs in a folder beside the
project, `<name>.gtr-fills/`, named by piece and the hash of what was sent, so a moved or changed piece is not given
an old fill. The project lists them (project version 8, with a migration). A missing folder means Mirror again, with
a notice, not an error. The command line exports them as saved and never calls the AI.

**Export.** The fill is placed as an image under the piece, clipped to the bleed band; the piece's original content
stays vector on top. This needs one sentence in `AGENTS.md` and `docs/architecture.md`: the original content is never
rasterised; an AI fill is an added picture, only in the bleed.

**Limits to state in the UI.** It fills the bleed, outside the piece. Inside the piece it only shows where the source
leaves the corners empty, as in item 8; it does not repaint white corners drawn in the PDF or in a scan.
`PRIVACY.md` and the README's Privacy section say that this sends pictures of the pieces to the chosen server.

Effort: L, the largest item in 1.3.0 (a new adapter path for two providers, the review dialog, the fills folder and
the project version).
